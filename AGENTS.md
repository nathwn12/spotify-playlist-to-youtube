# sp2yt — agent notes

## What it is

Keyless Spotify to YouTube Music playlist transfer for Windows. The server binds to 127.0.0.1:8787.

## Stack

- Python 3.12+, standard library only — no requirements file, no venv. Do not add dependencies (`backend.py` imports only the standard library).
- Three files do everything: `backend.py` (server + all transfer logic), `app.py` (PROD WebView2 shell), `index.html` (single-page UI). `watchdog.py` diagnoses failures from the audit log.

## Layout

The root is the app package and its standard controls: `backend.py`, `app.py`, `watchdog.py`, `index.html`, `pyproject.toml`, `AGENTS.md`, `README.md`, `CHANGELOG.md`, `LICENSE`. Everything else has a folder — `scripts\` for the `.cmd` helpers, `docs\` for documents, `tests\` for the gates and fixtures, `assets\` for images and icons. `sp2yt.exe`, `build\`, `dist\`, `build.log` and `sp2yt.spec` at the root are git-ignored build artifacts, not sources. Every script resolves the root from its own location (`cd /d "%~dp0.."` or `%%~fI`), so it runs from any working directory; add a root-level file only when no folder fits.

## Run / build

- **DEV (iterate here):** `python3 backend.py` (or `scripts\sp2yt-start.cmd`), open `http://127.0.0.1:8787`. No build step.
- **PROD:** run `scripts\build.cmd` (it cds to the repo root; needs `pyinstaller` + `pywebview`). It backs up the exe, kills running instances, compiles one portable `sp2yt.exe`, smoke-tests `/health`, deletes the backup on green / restores it on red. Never invoke `pyinstaller` directly — the backup/restore + smoke logic is the build.
- The gate is `scripts\acceptance.cmd`, which must print `36/36 fixtures` and then pass the language tests, the counts/API contract, the edition tests, the order/convergence tests, the cover tests, the page-script parse check, the UI checks, the cookie tests, the connect-card checks and the release-asset checks — every one green — before anything ships. The heavier offline suites are explicit: `tests/test_slices.py` (a 2,500-row transfer, ~20 s), `tests/test_repair.py` and `tests/test_scale_report.py`.
- **Lint / format:** `python3 -m ruff check .` and `python3 -m ruff format .`; the config is `pyproject.toml` (`target-version = "py312"`, rules `E,F,W,I,UP,B`). Outstanding findings are real debt, not a gate yet: fix them rule by rule, never with a mass reflow or `--unsafe-fixes`.
- Port is fixed at `8787`, bound to `127.0.0.1` only.

## Architecture quirks (unofficial surfaces)

- Spotify read = scrape of the public embed page `__NEXT_DATA__` for metadata, plus the keyless token path for titles past the 100-track cap (`fetch_spotify_tracks`). No login. If Spotify changes format, failure surfaces as `parse` — fix the parser, not the retry.
- YTM = InnerTube `WEB_REMIX` + the public web client key in `backend.py`. `SAPISIDHASH` is derived per call server-side (`yt_headers`) — it goes stale in minutes, so every call re-derives; don't cache headers.
- `POST /api/search-batch`: max **25 items/batch**, workers clamped **1–10** (default 8). Item failure is a skip (`videoId: None`), never a batch failure — don't "fix" this to raise.
- Playlist write (`transfer_create_append`): create carries ≤50 ids inline (`CREATE_INLINE_MAX`), then the outstanding copies go out in slices of 100 (`TRANSFER_SLICE`). A slice is followed by another only when its own read proves it: the read floor rises by the copies the server accepted, and every accepted copy of the slice must be present (an outside add padding the total is not evidence). Presence is counted BY ID, never by plan slot: copies of one videoId are indistinguishable in a read, so a copy that landed can be attributed to an earlier refused occurrence of its id, and asking "did slot i land" reports it absent. A read that stops before the end, or that hides a slice, sends nothing further. The final **ledger** is reconciled against the last completed read. Repeats are significant - N copies in ⇒ N entries out, and every add carries `"dedupeOption": "DEDUPE_OPTION_SKIP"` because a transfer is 1:1 with the source, always (there is no toggle; never dedupe `video_ids`). `duplicate` survives only for a server that refuses anyway, and only from its own duplicate toast.
- Convergence (`_converge`) counts copies, not ids: a repeated videoId the playlist holds once is one copy short and re-sending it is the repair, in plan order. The repair goes out through the same sender as the first pass (`_append_verify`: ≤100 copies, each batch proved by its own read-back), and its statuses are keyed by the copy's position in the plan. A copy the server refused (duplicate toast or plain refusal) is not re-sent in the same run - that verdict is final for it, and it ends as a named residual rather than a `complete` record; a copy whose write may have landed (a lost reply) is frozen the same way and never re-sent at all. A copy the server ACCEPTED that no complete read taken after the send shows is also an unknown write, not an absent one: the playlist grew by it, so the row may be on the playlist under a videoId this app cannot name. It is frozen by id, named with the manual recovery, and never re-sent by this run or a resume — and because the freeze is by ID, every other occurrence of those ids leaves the repair batch with it, not only the position that stalled. Without that, every pass (and every Ctrl+Enter) re-sends the same copies while the playlist grows by each send. Progress is the run's own copies resolving, never the playlist's row count, and it is measured against the previous read rather than the union of every read. `edit_playlist` can only append, so a repaired copy can land after a later one; `_order_preserved` reports that and `order_ok`/the done line say so, because a playlist holding every copy in a different order is not a faithful transfer.
- Live progress is the playlist's own word: `counts.added` is a copy a read proved present, `counts.pending` is one that was sent and not proved yet, and `/api/run`'s `attempted` counts both plus the terminal outcomes. A queued row is in none of them. A row the run never sent is `not_sent` (unverified, never `missing`): nothing asked the playlist for it. Mid-run, `added` only moves on a read that reached the end of the playlist; a partial read's presence is accounted for once, by the final ledger, in the open — so a seed read that stopped short publishes no landed row either. Recount from rows only (`_counts_from_rows` / `_run_counts_locked`), including on a run that matched nothing.
- An append's outcome has one failure class (`yt_add_one`): `STATUS_UNSURE <why>` for every failure whose application is unproven — a timeout, a closed connection, a 5xx, **and a 429** (the endpoint is unofficial, so a rate-limit reply is not proof the write was refused unapplied). An unknown copy is never re-sent by any automatic path, not inside the add, not by the repair pass, and not after a restart: `_reconcile` files it `unverified` (never `missing`, never blamed on a short read) with a manual recovery, the run ends `gaveup` naming it, and its position goes on disk. A 400/401/403/404 is a verdict, returned as-is so the run stops: `_create_new`, `_resume_incomplete` and the complete-record top-up all carry it out (`fatal`), `_transfer_thread` does not enter the repair pass, and `/api/run` serves it as `error` with `kind`/`hint` from the status alone (`_write_verdict`). A copy the run never sent is named "not sent" (`not_sent`) rather than counted as an entry a read proved absent. A record that cannot name the plan it was sent (`_NO_PLAN_MESSAGE`) is reported the same way: nothing is sent, the record is kept, and the advice is the manual check — never Reset, deleting the playlist, or removing `created.json`.
- An unknown write taints its whole song: copies of one videoId cannot be told apart in a read, so freezing one occurrence freezes every other occurrence of that id for the run (`_frozen_positions`). Sending the other copy could be the second row of a song the playlist already holds twice. An inline repeat is therefore unknown until a read can answer it, and duplicates are still allowed: a COMPLETE read that holds at least as many copies of the id as the doubt was recorded against proves the multiplicity without attributing copies, so the doubt is cleared and the rows land. The bar is the recorded multiplicity (`unsure_need`), never the current plan's count — a plan that shrank must not answer a two-copy doubt with one visible entry — and a doubt with no recorded multiplicity is never cleared at all.
- A slice's positions leave the write-ahead only when a read has settled them: `_note_outcomes` records the unknown replies immediately and the read-back clears the positions it proved (or that got a final verdict). A crash between an accepted add and its proof therefore leaves the chunk `inflight`, and the next run inherits a doubt instead of a copy that looks unsent. Both `_note_outcomes` calls are checked: an unknown the save could not make is erased by the NEXT save (which merges its own empty unknown set over the record), so a failed note stops the run. The freeze write is a gate for the same reason.
- A verdict on the CALL (400/401/403/404) ends the run where it was given: `_create_new`/`_resume_incomplete` return it (`fatal`), the repair pass is not entered, and `/api/run` serves it as `error` with `kind`/`hint` from the status alone (`_write_verdict`) — `reason` stays a fixed sentence with no status in it, and the hint names an expired session and a permission answer as the two possibilities because nothing here can tell them apart. A copy the run never sent is named "not sent" (`not_sent`) rather than counted as an entry a read proved absent.
- Unknowns are durable by videoId (`unsure_ids` + `unsure_need`), not just by position, and the write-ahead carries the multiplicity of what it queues (`inflight_need`) in the same save as the positions: a slice that dies before its outcomes are known still hands the next run a doubt it can answer. `_persisted_unknown` resolves saved positions through the plan the record wrote and returns the ids; `_adopt_plan` adopts a fresh plan while keeping an id the new plan no longer contains, so a later run that matches that song again still knows its copy is unproven and never resends it. A record that carries unknown positions but no plan to read them against raises `RecordUnreadable` rather than guessing which songs they are.
- A doubt is cleared only by evidence that can answer it, and the verdict never contradicts the record. `_converge` re-examines its frozen copies against every complete read (`resolve_unknowns`): an id the read holds as many copies of as the doubt was recorded against is resolved, and anything it cannot answer stays unresolved — so `done` is never written beside a `complete:false` that names an unknown copy. Every `_persist_final` call in the resume, top-up and converge paths carries the same guard.
- A create persists its intent before the request (`create_pending` plus the plan and title). A lost or unreadable reply leaves that record, and the failure sends the user to check their YouTube Music library for a playlist with that title — never to retry — and to KEEP it if it is there: that playlist holds the copies the create carried, so it is finished by hand, never deleted or Reset. A later run refuses to create a second playlist over the record and gives the same advice. `load_created` fails closed: a missing file is a first run, but a file that exists and cannot be read or parsed raises `RecordUnreadable`, so no run may create or overwrite a playlist over a record it cannot read — and the message keeps the evidence: nothing is removed or rewritten, the reader is told to take a safe copy first and to check the playlist that record may still name, never to delete or Reset it. `classify()` matches "cannot be read" before its generic create-reply branch for that reason.
- An inline copy no read has proved is unknown, not unsent. The create's record is written with EVERY inline copy unknown before the first read (the reply named the playlist, so the batch was taken and nothing has looked at it yet), and the first complete read narrows that set to the copies it does not account for — a read that stopped short clears none of them. A copy a COMPLETE read does not name (a read is padded with rows, so its length still matches while a specific id is gone) stays in `inline_unknown`: frozen by id, named, never re-sent. Appending it is one source row becoming two entries.
- A record's version gates its evidence, and only the protocol can award it. `_persist_incomplete` — the write that marks a new playlist — stamps `RECORD_VERSION`; `save_created` stamps nothing, so no unrelated save (a top-up's plan write, a progress write, a standby) can promote a record whose evidence is older. A record without the version is used only when `_legacy_safe` PROVES it: one complete read that holds every copy its own plan asks for, after which nothing ambiguous is left to write, its only remaining work being ids the source gained. Then — and only then — it is promoted. `complete:true` is not that proof (an older run interrupted while topping up left it over writes whose outcomes it had cleared), so the flag never substitutes for the read. A refused record raises before any write, names the playlist and what the read showed, keeps the record intact, and suggests only the manual check — never Reset or deleting anything, because the record is the only copy of the log, the plan and the playlist link. `_latest_incomplete` serves `resumable:false` with that reason.
- The top-up persists the plan its positions index (ids, slots) and re-expresses the unknown copies in that plan's positions, in one write (`_adopt_plan`) before the first send, so positions and the plan they mean are never persisted apart. Its read minimum is the LAST run's proven floor (`expected_min`), never this run's distinct count: a plan the source has grown cannot be held yet, and demanding it refused every newly added track. Saved positions are translated through the plan the record wrote (`_persisted_unknown`), and the unknown ids travel with the adopted plan. Its "nothing to send" branch may only write `complete:true` from a read that itself reached the end of the playlist and left nothing unknown: a partial or below-floor read is not evidence about the tail.
- Resuming never turns an unknown write into a fresh one. `_append_verify` writes each slice's positions to the record before the first add goes out (`inflight`, merged with what is already queued) and clears a position only once a read has settled it — its verdict is final, or its whole slice was proved — so a close between an accepted add and its read-back still leaves the doubt on disk; `_note_outcomes` records the unknown replies in between, and a freeze that cannot be saved raises before anything further is sent. The slice's outcomes and the accepted floor replace the queue (`unsure`, `expected_min`); `_resume_incomplete` restores both, freezes every position either list names (and their ids), and reads with `minimum=expected_min`, so a read that is short of what the run proved is incomplete rather than an authorisation to append. The complete-record top-up branch honours the same two fields and writes `complete:false` before its first send.
- Persistence is fail-closed and additive (`save_created`, `_persist_fields`): the record is written to a temp file and `os.replace`d, so a failed save can never truncate it; both return whether the bytes are on disk; `_append_verify` refuses to send when its write-ahead could not be saved, and `_create_new` refuses to append when the create's record could not be written. `expected_min` can only rise and `unsure`, `unsure_ids`, `unsure_need` can only grow, clamped in one place, so no stale writer can lower the floor or drop an unknown. The one write that may SHRINK the unknown set is `_set_unknown`, used only when a complete read resolved an id; it replaces ids, positions and need together.
- `complete` is only written when the final read reached the end of the playlist **and** every intended copy was read back (`added == len(plan) and read_complete`). A refused duplicate is a source row the playlist does not hold, so it no longer counts toward completeness.
- A server verdict blocks its own COPY, never a videoId: refusal positions and unknown positions are both keyed by the copy's position in the plan, so one occurrence being refused cannot deny a later occurrence that was never sent.
- Dupe-aware create (`yt_create_checked`): same `spotify_id` + live YTM copy ⇒ returns the existing playlist, creates nothing. Record lives in `created.json`.
- Script-aware matching (`_fold_text` → kana romanization → identified match): Japanese-script and romaji spellings of one title align, and a script-crossing row with no identified candidate is **skipped** with its reason — the rank-1 fallback is refused, never guessed, because rank 1 is the search engine's opinion. A `score` is a similarity index, never a probability. A candidate carried by its title alone is not a match either: an exact title with no artist agreement and no duration reading is refused as `title only` (`_supported`), and the next query variant gets its turn — that shape put an unrelated curator upload in a playlist at 0.70. Artist agreement alone, or a duration that is not plainly wrong, still matches. Latin-only rows still run the legacy scorer alone. An album-bearing query variant is tried **last**, only when the source row carries `album`, and an edition word in that album (deluxe/single/EP/remaster) breaks a near-tie among candidates already within 0.05 of the leader: a widening, never a gate.
- Soft second search (`_second_search_skipped`): a row whose search never answered (timeout, connection, 429, 5xx) is asked again once, with its own first query — sent with `yt_search(..., tries=1)` so the search's own three-attempt budget cannot multiply it — and the same evidence bar, capped at `SECOND_SEARCH_MAX` rows with one request each, and the pass stops at the first row that still fails on the wire or is refused outright. A skip that answered about the song is never re-searched; a row that resolves says `found on a second search`; a row still unresolved keeps its skip. This runs only on a fresh match (a resume replays its plan and searches nothing).
- Cover inheritance (`yt_set_playlist_cover`): a **newly created** playlist takes the Spotify cover through the 3-call resumable upload (handshake → upload → attach). Best-effort by construction — no cover, non-image bytes, a refused handshake or a failed attach is a silent skip, one `cover` audit line, and never a failed run. Never runs on a resume/top-up, so it cannot overwrite a hand-set cover.

## Cookie / state gotchas

- `normalize_cookie` accepts a typed `a=b; c=d` header **or** Netscape file content — preserve both paths.
- The vault is DPAPI-encrypted per Windows user; disk watchers (Desktop + Downloads plus one optional extra folder) re-latch by content markers. Logs record lengths/flags only — **never log or print cookie values**.
- Runtime state lives in the per-user application data folder (`sp2yt`), falling back to the repo dir if unwritable. All git-ignored — never commit `*.log`, vault/watch/created json, `sp2yt.exe`, `build/`, `dist/`, or `settings.json`.
- Diagnose via `python3 watchdog.py` (or `--watch` loop); errors carry `kind` (`auth`/`throttle`/`transient`/`parse`/`source`/`user`/`write`/`unknown`) + `hint` via `classify()`.

## Fixtures

- `tests/fixtures/playlist.json` holds 36 recorded rows — each with its real source row and the real YouTube Music search responses, trimmed to only the keys the parser reads. The six Japanese rows are hand-authored, not recorded: each carries its own `responses` map so rows sharing a source title can still replay different cards. The gate replays them offline through the real matcher in `backend.py`.
- Re-record when the matcher changes: `python3 tests\record_fixtures.py <public playlist url>` (at most 40 real searches, 300 ms apart; everything after that runs offline). `merge_rows` carries the hand-authored rows over, so only recorded rows are replaced. Review the printed `ok`/`skip` lines before committing the new fixture.

## Icons

- Live mark is `assets/icon.ico` built from `assets/icon-src.png`. To change it: replace both, rebuild via `scripts\build.cmd`, then run `scripts\refresh-shortcut.cmd` (rebuilds the Desktop shortcut + refreshes the Windows icon cache).
